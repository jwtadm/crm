# CRM 重构最终报告

**周期**：2026-11-02 首次提交 → 2026-11-12
**范围**：60 个提交，37 个文件，+8,197 / −1,010 行
**数据规模**：客户 54,188 人 / 平台账号 45,092 个 / SQLite 820MB / 日活数据 3 年内
**约束**：功能与业务逻辑不变、数据零丢失、不换框架、不迁数据库

---

## 一、一句话结论

慢的根本不是 SQLite，是**查询方式**：按天循环发 SQL、每次请求重算全表分布、
纯 Python 算 4096 维向量、每条新连接都让 64MB 页缓存冷启动。
这三类问题全部在原地解决，没有迁移数据库。

同时修掉了一批**会丢数据/会静默失败**的底层缺陷（并发写事务、409 仍提交、
批量任务必死、新库无法部署），并把前端从"能点"重做成一套有设计系统的界面。

## 三、修复的 Bug

### 3.1 数据正确性 / 可用性（最严重的一类）

1. **并发写入会丢数据**
   `db.tx()` 用 deferred `BEGIN`：读事务升级为写事务时，若别的连接已提交过，
   SQLite 直接抛 `SQLITE_BUSY_SNAPSHOT`，而调用方大多 `except Exception` 后当作成功。
   实测：320 次并发写里 299 次失败；另一组 640 次写只有 341 次落库。
   → 改为 `BEGIN IMMEDIATE`（写锁在事务开始时获取），并发写 0 失败。

2. **`/api/db/import_handle` 返回 409 时事务仍然提交**
   `return` 位于 `with db.tx()` 内部，正常退出即 COMMIT：客户端看到"失败"，
   但 people 行已插入、账号归属已改。→ 哨兵异常 `_AbortTx` 触发 ROLLBACK。
   用 AST 扫描全仓 32 处「tx 内 return」，确认仅此一处是写后返回。

3. **批量相似 / 批量补全跑一批就死**
   checkpoint 写 `last_checkpoint_at`，但两张 job 表都没有这一列；异常被吞后
   整个任务标 failed。→ 删除该列引用（watchdog 读的是 `payload_json`）。

4. **全新数据库无法从零部署**
   `SCHEMA` 里 3 个索引先于依赖的列/表创建，`executescript` 中途失败，
   后续迁移与 ANALYZE 全不执行 —— 新库只建出 4/25 个索引。
   → 索引移入 `_apply_migrations`，顺序问题消除。

5. **「全选匹配的」在最常用筛选上必然 500**
   4.3 万行拼成 4.3 万个 `?`，超过 SQLite 变量上限（32,766 / 999）。
   「待联系」覆盖 80% 客户表，等于该功能基本不可用。
   → 按 900 一批分块；并补上漏传的 `include_rejected`（选中数与表格行数对不上）。

6. **`email_log` 全程没有任何写入**
   看板的"发送邮件 / 成功"结构性恒为 0。→ 发信成功与失败都落库（同一事务），
   统计从此是真实值。**这是一次口径变更**：历史仍为 0，之后逐日累积。

7. **导出 xlsx 每次泄漏一个临时文件**
   `NamedTemporaryFile(delete=False)` 从不清理。→ 改为后台任务 + 内存/定时清理。

8. **删除有历史记录的用户直接 500**
   外键约束在最后一步才炸。→ 删除前用 `user_history_blockers()` 一次查出
   9 张表的引用计数，返回 400 + 具体阻塞项。

9. **ingest 响应体积膨胀 28 倍**、**两处随使用量/攻击流量无限增长的内存结构**
   （限流桶、内存任务缓存）→ 定时清理 + LRU 上限。

10. **输出不确定性**（会让"逻辑不变"的验证失效）
    `GROUP_CONCAT` 无 `ORDER BY`、`ORDER BY COUNT(*) DESC` 无 tie-break，
    加索引后第 10 名是谁会变。→ 全部补确定性排序键。

### 3.2 安全问题 / 加固

1. **内联 `onclick` 拼接用户名**
   `onDeleteHandle(1, '${escapeHtml(username)}')`：用户名里的引号会逃出 JS 字符串，
   属于存储型 XSS 向量。→ 改为 `data-*` 属性 + 事件委托，不再拼 JS 字符串。
2. **SQL 注入面审计**：全仓查询均为参数绑定；无字符串拼接 SQL。
   回归工具与扫描器均通过。
3. **权限**：员工只能看到自己名下数据（列表 / 统计 / 导出 / 批量），
   服务端二次校验，而非只靠前端隐藏。
4. **会话密钥持久化**（`.session_secret`），重启不再踢掉所有人。
5. **登录限流**（30 次/60s），桶表定时清扫，避免内存无限增长。
6. 遗留：Mimosa 扫描器仍报两条**低危**「不安全随机数」
   （`tools/similarity_canary.py:88`、`platforms/_tikhub.py:84`），
   均为非安全用途（采样/退避抖动），未改。

### 3.3 前端缺陷

| 问题 | 影响 |

## 四、性能报告

### 4.1 根因（为什么不是换数据库）

| 现象 | 真实原因 | 代价 |
|---|---|---|
| `/api/stats` 3.75s | 23 条独立聚合，多次 54k 行全表扫描 | 每次请求重算 |
| 趋势图 90 天 | 每天 7 条 SQL 的 Python 循环 | 630 次往返 |
| `settings.get()` | 每个 key 开一条新连接 | 100 人批次 = 600 条 |
| 相似度过滤 185s | 纯 Python 双循环算 4096 维余弦 | 39,874 × 16KB |
| `SELECT *` 批量补全 | 把 19KB/行 `raw` 与 embedding 一起拉进内存 | 峰值 1.2GB |
| 每条新连接 62ms | 64MB 页缓存冷启动（热连接同查询 32ms） | 一半时间在读刚解过的页 |

换成 MySQL 一条都不解决：630 次进程内调用会变成 630 次网络往返。

### 4.2 关键改动

- **趋势图**：按天循环 → 一条覆盖全区间、按 `(ts-start)/86400` 分桶的聚合，
  SQL 数与天数无关（5 条，795 天也一样）。
- **统计总览**：四个漏斗状态的 Python 循环 → 一条 `GROUP BY`。
- **只读连接池**：`db.ro()` 复用连接，避免每次 64MB 页缓存冷启动；
  写路径 `db.tx()` **不动**（失败事务不留给下一个调用者）。
- **numpy 矩阵化**：拒绝池一次预归一化 + 一次矩阵乘；
  与逐对余弦最大分数差 1.5e-07，argmax 0 处不一致，距 0.88 阈值最近 6.0e-03。
  numpy 为可选依赖，缺失自动回退原实现。
- **覆盖索引**：平台/认证/商务三个分布 217ms → 5ms；按粉丝排序 127 → 53ms。
  同时删除 3 个冗余索引，降低热表写放大。
- **JSON1 `json_each`** 统计标签：56ms → 12ms，输出逐项一致（无 JSON1 则回退）。
- **启动不再无条件 `ANALYZE`**：62ms → `PRAGMA optimize` 0.6ms。
- **静态资源**：`style.css?v=<内容哈希>` + 一年 `immutable`；
  首屏 61.5KB → 14.3KB（zstd），二次访问 **0 字节**。

### 4.3 全量体检（86 个路由）

| 分类 | 数量 | 中位 | 最差 p95 |
|---|---|---|---|
| SSR 页面 | 12 | 2.5 ms | 3.0 ms |
| GET 接口（含参数变体） | 35 | 2.5 ms | 78 ms（按粉丝排序） |
| 写接口 | 18 | 4.1 ms | 19 ms（hydrate） |

**没有任何读路径超过 100ms。**

并发：8 线程读/写 0 错误；写并发 p95 175ms（WAL + busy_timeout 吸收排队）。
多进程：1/2/4/8 进程 = 41 / 73 / 123 / **184 req/s**，7.68× 近线性扩展。

### 4.4 资源占用（生产 mcz，4 核 / 7.4GB）

| 阶段 | RSS |
|---|---|
| Python 裸解释器 | 12 MB |
| 导入 app + 建表 | 80 MB |
| 服务读请求（池热） | 120 MB |
| + 相似度任务（拒绝池矩阵） | 201 MB（改造前 1,038 MB） |
| + 批量任务快照 | 250 MB |
| 导出 xlsx 峰值 | 563 MB |
| 空转 CPU | 0.0% |

生产当前 1 master + 8 worker ≈ 1.4GB。**建议改为 4 worker**（= 核心数）：
8 个 sync worker 在 4 核上不提吞吐，却让每份进程内缓存各复制一份，可省约 700MB。

## 五、功能性变更（用户可见）

### 新增

- **员工管理**：新增员工（服务端生成 12 位临时密码、首次登录强制改密）、
  停用/启用、重置密码、角色升降、删除前阻塞项提示、审计日志。

- **界面主题**：靛紫 / 深海 / 落日 三套，存浏览器、首屏前生效。
- **日期选择器**：自绘日历（周一起始、今天/清除/确定），替换原生
  `input[type=date]` 与 `datetime-local`。
- **加载反馈**：全局顶部进度条（130ms 后才出现）、列表/统计/抽屉骨架屏、
  按钮内嵌 spinner、内容淡入。
- **分页**：三个列表统一 20 条/批 + 滚轮分页，且都关在 480px 内层滚动框里；
  `/database` 从"最多 500 条"变为不限量。
- **账号安全页**：重做修改密码流程（显示/隐藏、强度提示、临时密码横幅）。

### 口径修正

- **本周/本月趋势图**：改为与 KPI 完全相同的窗口（本周一 / 本月 1 日 → 今天），
  不再是"最近 7 / 30 天"；自定义区间与员工筛选也会同步刷新图表。
- **标记不合适**：按所选区间内的状态变更事件计数（不是当前快照），
  与「拒绝分析（全量）」在标题上分别标注，避免误读。
- **平台分布/合作强度/热标签/拒绝分析**：本来就是全量口径，标题补「全量」徽标。
- **发送邮件 / 成功**：从结构性恒 0 变为真实值（历史不回填）。

### 兼容性

- 前端 API 契约未变：响应键名、`error` 字符串判别、`409 + job_id` 形状保持。
- 业务规则未变：状态不降级、合并去重策略、权限矩阵、Asia/Shanghai 口径。
- 部署新增依赖：`numpy`（可选，缺失回退）、`xlsxwriter`（导出必需）。

## 八、没做 / 仍建议做

### 已完成但值得知道的取舍

- 不换框架、不引 ORM、不拆多实例（自用产品，已明确否决）。
- `app.py` 未拆 Blueprint：纯结构调整，不解决性能，却放大回归面。
- 写路径连接不复用：收益不值得"失败事务状态泄漏给下一个调用者"的风险。

### 仍建议排期

1. **高可用（基础设施，UI 改不动）**
   - `sqlite3 .backup` 每小时 + 保留 7 天 + 每日异地同步
   - `/api/health` + systemd `Restart=always`
   - gunicorn `--workers 4`
   - 后台任务拆独立进程，避免重启 web 打断批量任务
2. **`raw` / `bio_embedding` 拆侧表**（820MB 级迁移）
   16–19KB 的大字段与热列同页，读轻列也要加载 blob 页；需独立备份 + 字节级校验。
3. **内联 JS 抽出为静态文件**：`people.html` 光脚本 40KB+，抽公共部分可让跨页面缓存生效。
4. **搜索/排序再提速**：FTS5（搜索）、把 `max_followers` 冗余到 `people`（排序），
   都是"结构换速度"，有漂移风险，建议等真实抱怨再做。

## 九、部署

```bash
# 1. 备份（必须）
ssh mcz "cp /opt/ig_scraper/scout.db /opt/ig_scraper/scout.db.bak-$(date +%F)"

# 2. 拉代码 + 装依赖
ssh mcz "cd /opt/ig_scraper && git pull origin master && .venv/bin/pip install -r requirements.txt"

# 3. 重启
ssh mcz "systemctl restart ig-scraper"
```

首次启动自动补建索引（一次性约 600ms / +2MB），并删除 3 个冗余索引。
回滚：`git revert` 对应提交即可，索引层面不影响正确性。
